This playbook covers the steps Quillstack support engineers and on-call staff must follow when a security incident is reported or detected. An incident includes any suspected breach, unauthorized access, leaked credentials, vulnerability disclosure, or abuse of the platform. Follow these procedures to contain the issue, notify the right people, and coordinate a response.

## Before you start

You need access to the admin console at admin.quillstack.internal, the #security-incidents Slack channel, and the security@ mailbox. Only on-call engineers, security leads, and senior support staff have this access. If you are triaging a report sent to security@quillstack.com and you are not on the security rotation, immediately forward the email to #security-incidents and page the on-call security engineer using the /page command.

Quillstack acknowledges every security report within 2 business days, but critical incidents require faster action. If a report describes active exploitation, credentials visible in public, or customer data exposure, treat it as P0 and page immediately even outside business hours.

## Steps

1. Open the admin console at admin.quillstack.internal and search for the affected workspace, user, or API key using the identifier from the report.
2. Post in #security-incidents with the report summary, the workspace ID if known, and the severity you are assigning: P0 (active breach, data exposed), P1 (vulnerability with proof of concept, no active exploit), or P2 (theoretical issue, no reproduction).
3. If the incident involves a compromised API key, revoke it immediately from the admin console under API Keys > Revoke, which returns error QS-1041 to any further requests. Document the key prefix, workspace ID, and revocation timestamp in the incident thread.
4. If the incident involves suspected account takeover or brute force, check the sign-in logs for the user. After 5 failed sign-in attempts the account is locked for 15 minutes, but if you see coordinated attempts from many IPs or credential stuffing patterns, escalate to the security lead and consider a temporary IP block.
5. Send the acknowledgment email to the reporter within 2 business days (or immediately for P0). Use the template in the #security-incidents topic: thank them, confirm receipt, give an initial severity, and set an expectation for follow-up (P0: within 24 hours; P1: within 5 business days; P2: within 10 business days). Do not disclose internal tooling, customer names, or details about other reports.
6. Create an issue in the bug tracker with the label security-incident and the prefix SI- (for example SI-2408-003). Attach the reporter's email, your initial findings, and the revocation or containment actions you have taken.
7. If the incident requires a code fix, loop in the engineering lead and request a patch timeline. Critical vulnerabilities (P0 and P1) trigger an out-of-band release; P2 issues go into the next scheduled release.
8. For incidents affecting customer data (read or write access by an unauthorized party, data visible in logs, export sent to wrong email), notify the affected workspace Owner by email within 24 hours. Use the breach notification template from the legal team (available in the playbook folder in the internal wiki). CC compliance@quillstack.internal and do not send this email without review by the security lead.

## Disclosure and follow-up

After the vulnerability is fixed and deployed, reply to the reporter with the resolution, the version or date of the fix, and thanks for the report. Quillstack does not run a paid bug bounty program, but if the reporter asks for recognition, add their name (with permission) to the security acknowledgments page on the public site.

If the reporter requests a CVE, forward the request to the security lead, who coordinates with MITRE. Do not assign a CVE yourself. The security lead also decides whether a public advisory is needed; if so, the advisory is posted to status.quillstack.com and emailed to every workspace Owner on the affected plan.

Update the SI- issue with the final timeline, the deployed fix, and any customer notifications sent. Close the issue only after the reporter confirms the fix or 30 days pass with no reply.

## Escalation

Page the on-call security engineer for P0 incidents, suspected ongoing breaches, or if you see signs of coordinated abuse (many workspaces hit at once, API keys leaked in public repositories, phishing targeting Quillstack users). The security lead decides whether to involve legal, PR, or executive leadership. Do not post about active incidents in public Slack channels or mention customer names outside #security-incidents.

If the incident involves payment data, PCI scope, or the billing system, page the infrastructure lead as well and follow the separate PCI incident runbook (internal wiki under Compliance > PCI-DSS).
