This runbook covers detecting, triaging, and resolving API outages and spikes in QS-1099 internal server errors. When QS-1099 rates exceed baseline thresholds, the on-call engineer investigates the root cause, mitigates customer impact, and coordinates with the engineering team for resolution. Follow these steps to diagnose the issue, communicate status, and restore service.

## Before you start

You need access to the admin console at admin.quillstack.internal, the PagerDuty incident, and the #on-call-api Slack channel. Confirm you can view real-time error metrics in Datadog (dashboard: API Health Overview) and access the incident response doc template in Notion. If the alert fired outside business hours, page the API team lead using the PagerDuty escalation policy "API Critical". Error QS-1099 is an internal server error; customers are told to retry after 60 seconds and quote the request_id from the response when contacting support, so every QS-1099 incident generates support volume.

Check the current QS-1099 rate in Datadog. Baseline is under 0.1% of total API requests. If the rate exceeds 2% for more than 5 minutes, the alert fires. Spikes above 10% indicate a severe outage. Note the time the spike began and whether it affects all endpoints or specific routes. Review the last 10 request_id values from the error logs to identify patterns (same workspace, same endpoint, same API key prefix).

## Steps

1. Acknowledge the PagerDuty incident and post in #on-call-api that you are investigating, including the current QS-1099 rate and affected time window.
2. Open the admin console at admin.quillstack.internal and navigate to Monitoring > API Errors > QS-1099 Stream to see live errors with full request details.
3. Check the "Top Failing Endpoints" widget. If one endpoint accounts for more than 50% of errors, the issue is likely route-specific; if errors are distributed evenly, suspect infrastructure (database, cache, or gateway).
4. Query the request logs for the last 15 minutes using the admin console log search: `error_code:QS-1099 timestamp:>now-15m`. Export the top 100 results as CSV and inspect the request_id, workspace_id, endpoint, and response_time_ms columns.
5. Cross-reference workspace_id values with the customer database. If the same 2-3 workspaces appear in most errors, the issue may be workspace-specific (large export, runaway webhook loop, or malformed data). If workspace_id is distributed, the issue is systemic.
6. Check for rate-limit correlation: run the query `error_code:QS-1029 timestamp:>now-15m` to see if QS-1029 (rate limit exceeded) spiked at the same time. When the rate limit is exceeded the API returns HTTP 429 with error code QS-1029 and a Retry-After header giving the wait in seconds. If QS-1029 and QS-1099 both spiked, a single customer may be hammering the API and triggering cascading failures. The API rate limit is 600 requests per minute per API key, so verify whether any single API key exceeded this threshold in the Rate Limit Dashboard.
7. Open an incident doc from the template and record your findings: start time, QS-1099 rate, affected endpoints, suspected root cause, and customer impact estimate (number of affected workspaces, number of failed requests).
8. If the root cause is identified and you can mitigate it (for example, disabling a misbehaving API key or restarting a specific service), proceed with mitigation and monitor the QS-1099 rate for 5 minutes. If the rate drops below 0.5%, the incident is resolved.
9. If the root cause is not clear within 15 minutes, escalate to the API team lead and the engineering manager on call. Post in #on-call-api with the incident doc link and request immediate triage.
10. Once the incident is resolved, post a summary in #on-call-api and update the PagerDuty incident with resolution notes. File a post-incident review issue in the bug tracker (label: post-mortem, priority: P1) within 24 hours.

## Troubleshooting

If QS-1099 errors persist after restarting the API service, check the database connection pool. A saturated pool causes timeouts that surface as QS-1099. The admin console shows pool utilization under Monitoring > Database > Connection Pools. If utilization is above 90%, increase the pool size temporarily (requires engineering approval) or identify and kill long-running queries in the database admin panel.

If errors are concentrated in export endpoints (POST /v2/exports), check the export job queue length in the admin console under Jobs > Export Queue. A backlog over 500 jobs indicates the export workers are overwhelmed. Restart the export worker pool and monitor queue drain rate. If the queue does not drain within 30 minutes, page the infrastructure team.

If the incident began immediately after a deployment, roll back the last release from the admin console under Deployments > Rollback. Select the previous stable version and confirm rollback. Monitor QS-1099 rates for 5 minutes post-rollback. If errors stop, the deployment introduced a regression; file a critical bug against the release and notify the engineering team in #engineering-alerts.
