The Quillstack API lets you build integrations, automate workflows, and manage workspaces programmatically. Every request requires an API key for authentication. This article covers base concepts, authentication, and common error codes you will encounter when working with the API.

## Before you start

You need an active Quillstack workspace and permission to create API keys. Owners, Admins, and Editors can create keys under Settings > Integrations > API keys. The number of active keys you can have depends on your plan: 1 on Free, 10 on Team, and 50 on Business. Review your plan limits before you start building.

## How authentication works

The Quillstack API uses bearer token authentication. Every request must include an Authorization header with your API key. The base URL for all endpoints is https://api.quillstack.com/v2. API keys begin with the prefix qs_live_ and are shown in full only once, at the moment of creation. If you lose a key you must create a new one and revoke the old one.

Here is an example request that lists pages in your workspace:

```bash
curl -X GET https://api.quillstack.com/v2/pages \
  -H "Authorization: Bearer qs_live_abc123def456ghi789jkl012mno345"
```

The API returns JSON for every response. Successful requests return HTTP 2xx status codes. Errors return 4xx or 5xx codes with a JSON body that includes an error code and message.

## Common error codes

Error QS-1003 means the request has no Authorization header. Check that you are sending the header on every request and that the header name is spelled correctly. Error QS-1007 means the request body failed validation and the response field errors lists each invalid field. Review the API documentation for the endpoint to confirm you are sending the correct fields and data types. Error QS-1013 means the resource does not exist or the key's workspace cannot access it. This happens when you request a page, task, or project by an ID that does not exist or belongs to a different workspace.

The table below lists these codes and their meanings:

| Error Code | Meaning | Action |
|------------|---------|--------|
| QS-1003 | Missing Authorization header | Add the Authorization header to your request |
| QS-1007 | Request validation failed | Check the errors field in the response |
| QS-1013 | Resource not found or inaccessible | Verify the resource ID and workspace |

## Response format

Every successful response includes a data field with the requested resource or list of resources. Error responses include code, message, and request_id fields. The request_id is useful when you contact support about a specific request. List endpoints return paginated results; see the pagination article for details on how to retrieve all pages.

## Security and key management

Store API keys securely and never commit them to version control or expose them in client-side code. Rotate keys regularly before they expire. Each plan has a different expiry period: 30 days on Free, 90 days on Team, and 365 days on Business. If a key is compromised, revoke it immediately under Settings > Integrations > API keys. Revoking a key cannot be undone, and any integration using that key will stop working immediately.

## Troubleshooting

If you receive an error response, check the code field first. Most errors are caused by missing or invalid request data. The message field usually explains what went wrong. If the error code is QS-1099, it indicates an internal server error; wait 60 seconds and retry the request. If the problem persists, contact support and include the request_id from the response.

When testing your integration, start with a single request to a simple endpoint like GET /v2/workspaces/current to confirm your authentication is working. Once that succeeds, move on to more complex operations like creating or updating resources.
