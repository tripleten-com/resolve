The Quillstack API enforces a rate limit to ensure fair usage and protect service availability. If your integration exceeds the limit, requests are rejected until the rate window resets. This article explains how the limit works and how to handle rate limit errors in your code.

## Before you start

The API rate limit is 600 requests per minute per API key. The limit applies to each key individually, so if you have multiple keys they each get their own quota. The rate window is a sliding 60-second period, not a fixed clock minute. If you send 600 requests in 10 seconds, you must wait 50 seconds before the oldest requests age out of the window and you can send more.

## How the rate limit works

Every successful or failed request counts toward your rate limit, including requests that return errors like QS-1007 or QS-1013. Only requests that fail at the network level before reaching the API server do not count. The limit is enforced per API key, so two integrations using different keys do not share a quota.

When the rate limit is exceeded the API returns HTTP 429 with error code QS-1029 and a Retry-After header giving the wait in seconds. Your integration should read this header and pause before retrying. The response body looks like this:

```json
{
  "code": "QS-1029",
  "message": "Rate limit exceeded",
  "request_id": "req_3m4n5p6q7r8s9t0u",
  "retry_after": 42
}
```

The retry_after field and the Retry-After header both give the same value: the number of seconds you should wait before sending another request. Do not retry immediately or you will continue to hit the limit.

## Steps to handle rate limits

Follow these steps to handle rate limit errors gracefully:

1. Check the HTTP status code on every response. If it is 429, read the Retry-After header.
2. Pause for the number of seconds given in the header before retrying the request.
3. Implement exponential backoff if you continue to hit the limit after the first retry.
4. Log rate limit errors so you can analyze usage patterns and optimize your integration.

Here is an example in Python that handles rate limits:

```python
import requests
import time

url = "https://api.quillstack.com/v2/pages"
headers = {"Authorization": "Bearer qs_live_abc123"}

while True:
    response = requests.get(url, headers=headers)
    if response.status_code == 429:
        retry_after = int(response.headers.get("Retry-After", 60))
        time.sleep(retry_after)
        continue
    break
```

## How to reduce rate limit errors

If you frequently hit the rate limit, optimize your integration to send fewer requests. Batch operations where possible, cache responses that do not change often, and avoid polling endpoints repeatedly. Use webhooks instead of polling for real-time updates. If your use case requires more than 600 requests per minute, create multiple API keys and distribute the load across them. Each key gets its own rate limit.

The table below shows example usage patterns and whether they are likely to hit the limit:

| Usage pattern | Requests per minute | Likely to hit limit? |
|---------------|---------------------|---------------------|
| Sync 50 pages every 5 minutes | 10 | No |
| Poll task updates every second | 60 | No |
| Bulk import 1000 tasks | 1000 | Yes |
| Webhook receiver (passive) | 0 | No |

## Troubleshooting

If you receive HTTP 429 but the Retry-After header is missing, wait 60 seconds before retrying. If you consistently hit the rate limit even after implementing backoff, review your request logs to identify which operations are most frequent. You may be polling an endpoint unnecessarily or making redundant requests.

If you see rate limit errors but your integration is sending fewer than 600 requests per minute, check that you are not sharing the same API key across multiple processes or servers. Each instance will contribute to the same rate limit. Create separate keys for each process to avoid this issue.
