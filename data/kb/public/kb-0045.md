API keys expire after a fixed period and must be rotated before they expire to avoid disruption. Rotating means creating a new key, updating every service that calls the API, and then revoking the old key. This article walks through the rotation process and explains how to do it safely without downtime.

## Before you start

You need Admin or Owner permissions to create and revoke API keys. Check your current key's expiry date under Settings > Integrations > API keys before you start the rotation. API keys expire after 30 days on the Free plan, 90 days on Team, and 365 days on Business.

Each workspace has a limit on active API keys: 1 on Free, 10 on Team, and 50 on Business. If you have reached the limit you must revoke an existing key before creating a new one. For a zero-downtime rotation, create the new key first, deploy it to every service, and only then revoke the old one.

## Steps

1. Sign in to app.quillstack.com and open **Settings > Integrations > API keys**.
2. Click **Create API key** and give the new key a descriptive name that includes the current date, for example `Production key 2024-08`.
3. Copy the full key immediately—it begins with `qs_live_` and is shown only once. Store it in a secure location such as a password manager or secrets vault.
4. Update every service, script, or integration that calls the Quillstack API to use the new key in the `Authorization: Bearer` header.
5. Test each service to confirm it can authenticate with the new key and complete a successful request.
6. Return to **Settings > Integrations > API keys** and click **Revoke** next to the old key.
7. Confirm the revocation—this is immediate and cannot be undone.

The old key stops working as soon as you revoke it. If you accidentally revoke the wrong key, create a new one and redeploy it; revoked keys cannot be restored.

## How key expiry works

Quillstack automatically expires API keys to limit the damage if a key is leaked. The expiry period depends on your plan:

| Plan     | Expiry period | Active key limit |
|----------|---------------|------------------|
| Free     | 30 days       | 1                |
| Team     | 90 days       | 10               |
| Business | 365 days      | 50               |

When a key expires, API requests return error code QS-1042 and you must create a new key. Quillstack sends an email reminder to workspace Admins and Owners 7 days before a key expires. Set a calendar reminder to rotate keys before they expire so you can plan the rotation during a maintenance window.

## Rotation strategies

For production environments, use overlapping keys to avoid downtime. Create the new key while the old one is still valid, update every service over the course of a few hours or days, verify that no service is still using the old key by checking your logs, and then revoke the old key. This approach means both keys are active for a short period, which is why the active key limit on Team and Business allows multiple keys.

If you maintain multiple environments (staging, production), create a separate key for each and rotate them on different schedules. Name each key clearly so you know which environment it belongs to: `Staging key 2024-08`, `Production key 2024-08`. This isolation prevents a compromised staging key from affecting production.

If your plan allows only 1 active key, you cannot overlap keys and must accept a brief window of downtime during the rotation. Create the new key, revoke the old one immediately, and deploy the new key as quickly as possible. Schedule this rotation during low-traffic hours.

## Troubleshooting

**I revoked the wrong key and my services are failing.** Create a new key immediately and redeploy it. Revoked keys cannot be restored, so the only fix is to create and distribute a new one. This is why you should always test the new key in at least one service before revoking the old one.

**I created a new key but forgot to copy it.** The full key is shown only once at creation. You cannot retrieve it later, so you must revoke the key and create a new one. Store the new key in a secure location immediately after creation.

**My services are still using the old key after rotation.** Check your deployment logs and confirm that every service, cron job, and integration has been updated with the new key. A common mistake is updating the key in one environment but forgetting a staging environment or a scheduled task.

**I am at the active key limit and cannot create a new key.** Revoke an unused or expired key first. If every key is still in use, you must accept downtime during rotation: revoke one key, create the new one, and redeploy it as quickly as possible.
