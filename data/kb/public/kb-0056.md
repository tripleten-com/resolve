If an API key is leaked, committed to a public repository, or otherwise exposed, you must revoke it immediately to prevent unauthorized access to your workspace. This article explains how to revoke a key and rotate to a new one with minimal downtime.

## Before you start

API keys begin with the prefix qs_live_ and are shown in full only once, at the moment of creation. After a key is revoked, any request using it receives error QS-1041 and HTTP 401. Error QS-1041 means the API key is invalid or has been revoked. You need Admin or Owner permissions to manage API keys under Settings > Integrations > API keys.

## Steps

### Revoke the compromised key

1. Sign in to app.quillstack.com and open Settings > Integrations > API keys.
2. Locate the compromised key in the list (keys are identified by a label you provided when creating them and the last 4 characters, for example "Production key (...xyz4)").
3. Click the key to open its detail page.
4. Click **Revoke key**.
5. Confirm the revocation in the dialog.

The key is revoked immediately. Any service or script using this key will start receiving error QS-1041 on the next request. Revocation is permanent and cannot be undone; you cannot re-enable a revoked key.

### Create and deploy a new key

1. On the API keys page, click **Create API key**.
2. Enter a label that identifies where this key will be used (for example, "Production key - rotated Aug 2024").
3. Copy the full key value immediately; it is displayed only once.
4. Update your application, script, or CI/CD pipeline to use the new key.
5. Test that the new key works by making a test API request.
6. Once confirmed, delete the old key value from any environment variables, secrets managers, or configuration files where it was stored.

If the compromised key was used in multiple places, update all of them before revoking the old key to avoid service disruption. Alternatively, create the new key first, deploy it everywhere, verify it works, and then revoke the old key.

## Report the exposure

If the key was exposed in a public repository, Slack channel, support ticket, or anywhere outside your organization, report it to Quillstack's security team:

1. Email security@quillstack.com with the subject "API key exposure".
2. Include the last 4 characters of the revoked key and where it was exposed (for example, "GitHub repository myorg/myrepo, commit abc123").
3. Confirm that you have revoked the key and rotated to a new one.

Security vulnerabilities are reported to security@quillstack.com; Quillstack acknowledges reports within 2 business days and does not run a paid bug bounty program. The security team may investigate whether the key was used by unauthorized parties before it was revoked.

## Troubleshooting

**Can I see which requests used the compromised key?** If you are on the Business plan, check the audit log under Settings > Security > Audit log. The log shows API requests by key ID, IP address, and timestamp. On Free and Team plans, audit logs are not available; contact support if you need help investigating suspicious activity.

**How do I prevent leaks in the future?** Store API keys in a secrets manager (for example, AWS Secrets Manager, HashiCorp Vault, or your CI/CD platform's encrypted secrets). Never commit keys to version control. Use environment variables or configuration files that are excluded from git (add them to .gitignore).

**I revoked the key but my app still works.** Your app may have cached the key or may be using a different key. Verify that you revoked the correct key by checking the last 4 characters, and confirm your app is actually sending the revoked key in the Authorization header.

**What if I do not know where the key was used?** Revoke it anyway. A leaked key is a security risk even if you are not sure where it was deployed. After revoking, monitor your application logs for authentication errors (QS-1041) to identify which services were using the old key, then update them with the new key.
