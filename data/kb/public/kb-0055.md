Error QS-1099 indicates an internal server error on Quillstack's side. Unlike client errors (4xx codes), this is not caused by your request, and the correct response is to retry after a short delay and report persistent failures to support.

## Before you start

Error QS-1099 is an internal server error; retry after 60 seconds and quote the request_id from the response when contacting support. Every QS-1099 response includes a unique `request_id` that helps the engineering team trace the issue in server logs. Do not discard this value.

## What QS-1099 means

When you receive QS-1099, something went wrong inside the Quillstack API that prevented it from fulfilling your request. This could be a transient issue (temporary overload, brief database unavailability) or a bug triggered by specific conditions. The error response looks like this:

```json
{
  "error": {
    "code": "QS-1099",
    "message": "An internal error occurred while processing your request",
    "request_id": "req_xyz789abc"
  }
}
```

The HTTP status is always 500. Unlike validation errors (QS-1007) or authentication errors (QS-1041, QS-1042), you cannot fix QS-1099 by changing your request. The API itself needs to recover or be fixed.

## Steps

### Retry with exponential backoff

1. When you receive QS-1099, wait 60 seconds before retrying the same request.
2. If the retry also returns QS-1099, wait 120 seconds and try again.
3. If the second retry fails, wait 240 seconds.
4. After three failed attempts, stop retrying and contact support with all three `request_id` values.

This pattern avoids overwhelming the API during an outage while giving transient issues time to resolve. Most QS-1099 errors clear within the first retry.

### Contact support

If the error persists after three retries or if you see a sudden spike in QS-1099 responses across many requests, contact support immediately:

1. Open a ticket at app.quillstack.com or email support@quillstack.com.
2. Include the `request_id` from the error response (or all IDs if you retried multiple times).
3. Describe what operation you were attempting (for example, "Creating a page via POST /pages" or "Listing tasks in project PRJ-42").
4. Note the approximate time when the errors started and how many requests are affected.

Support uses the `request_id` to locate the exact request in server logs and diagnose the root cause. Without the ID, investigation takes significantly longer.

## Troubleshooting

**Should I retry immediately or wait 60 seconds?** Always wait at least 60 seconds. Immediate retries can make the problem worse if the API is experiencing load issues. Exponential backoff gives the system time to recover.

**I am getting QS-1099 on every request.** This suggests a wider API outage. Check the Quillstack status page at status.quillstack.com for incident updates, and contact support if no incident is posted.

**Can I prevent QS-1099 by changing my request?** No. QS-1099 is not caused by invalid input or incorrect authentication. The issue is on Quillstack's infrastructure, and your request may be perfectly valid. Retry the exact same request after waiting.

**What if the request was a write operation (POST, PUT, DELETE)?** Be cautious when retrying writes. If the first request succeeded internally but failed to send a response, a retry could create a duplicate resource. Check whether the operation completed (for example, query for the resource by ID) before retrying a write.
