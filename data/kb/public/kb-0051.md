When Quillstack delivers a webhook event to your endpoint, it expects a 2xx HTTP response to confirm receipt. If your endpoint returns an error or times out, Quillstack automatically retries the delivery. This article explains how the retry mechanism works and what to do when an endpoint is disabled after repeated failures.

## Before you start

You need Admin or Owner permissions to manage webhook endpoints under Settings > Integrations > Webhooks. Each endpoint you configure receives events for the workspace where it was created.

## How retries work

A webhook delivery that does not receive a 2xx response is retried up to 5 times with exponential backoff over 24 hours. The retry schedule is:

| Attempt | Delay after failure |
|---------|---------------------|
| 1       | Immediate (original delivery) |
| 2       | 1 minute |
| 3       | 10 minutes |
| 4       | 1 hour |
| 5       | 6 hours |
| 6       | 16 hours |

If all 6 attempts fail, Quillstack disables the endpoint to prevent further failed deliveries. You will receive an email notification when this happens, and the endpoint status changes to "Disabled" in Settings > Integrations > Webhooks.

## Error QS-1061: endpoint disabled

Error QS-1061 means the webhook endpoint was disabled after repeated failed deliveries and must be re-enabled under Settings > Integrations > Webhooks. When you try to create or update a webhook configuration pointing to a disabled endpoint, the API returns:

```json
{
  "error": {
    "code": "QS-1061",
    "message": "Webhook endpoint is disabled due to repeated delivery failures",
    "request_id": "req_abc123xyz"
  }
}
```

You cannot send new events to a disabled endpoint until you fix the underlying issue and re-enable it.

## Steps

### Re-enable a disabled endpoint

1. Sign in to app.quillstack.com and open Settings > Integrations > Webhooks.
2. Locate the endpoint marked "Disabled" in the status column.
3. Click the endpoint URL to open its detail page.
4. Review the delivery log to identify why deliveries failed (timeouts, 500 errors, certificate issues).
5. Fix the issue on your server: ensure your endpoint returns a 2xx response within 10 seconds and accepts POST requests with a valid TLS certificate.
6. Click **Re-enable endpoint**.
7. Send a test event by clicking **Send test event** and verify your server receives it and responds with 200 OK.

The endpoint is now active again and will receive new events. Past failed deliveries are not retried automatically.

## Troubleshooting

**Why was my endpoint disabled?** Check the delivery log under the endpoint detail page. Common causes include server timeouts (no response within 10 seconds), certificate errors (expired or self-signed TLS certificates), and 5xx server errors.

**Can I retrieve the events that failed?** No. Quillstack does not queue failed events indefinitely. Once an endpoint is disabled, any events that occurred during the retry period are lost. Re-enabling the endpoint only applies to new events going forward.

**How do I test my endpoint before re-enabling?** Use the **Send test event** button on the endpoint detail page. This sends a sample `page.created` event and displays the response. If the test succeeds (2xx response), you can safely re-enable the endpoint.

**What if my endpoint is slow but reliable?** Ensure your endpoint responds within 10 seconds. If processing takes longer, return 200 OK immediately and handle the event asynchronously in a background job. Quillstack considers any response after 10 seconds a timeout and will retry.
